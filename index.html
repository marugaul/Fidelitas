Paradigmas
Paradigma 01 / 08

Programación
Imperativa

Le dices a la computadora exactamente cómo hacer cada cosa, paso a paso. El programa es una secuencia de instrucciones que van cambiando el estado de las variables. Es el paradigma más cercano al hardware — así funciona la máquina debajo de todo. Lenguajes representativos: C, Pascal.

estado mutable variables bucles condicionales secuencia de pasos asignación
Python
# Suma de cuadrados de números pares del 1 al 10
# Instrucción por instrucción — el programador controla todo

total = 0
i = 1

while i <= 10:
    if i % 2 == 0:               # ¿Es par?
        cuadrado = i * i
        total = total + cuadrado
    i = i + 1

print("Suma de cuadrados de pares:", total)
# → 220   (4 + 16 + 36 + 64 + 100)
¿Por qué esto es imperativo?
total = 0 / i = 1 Estado inicial explícito. El programa depende de variables que guardan el estado. Sin estas dos líneas, no hay nada que acumular ni iterar.
while i <= 10: Control de flujo manual. El programador decide cuándo empieza y cuándo termina. La máquina no sabe nada — nosotros le decimos hasta cuándo iterar.
if i % 2 == 0: Decisión explícita en cada paso. Evaluamos una condición y elegimos qué hacer. Es el programador guiando cada bifurcación del camino.
total = total + cuadrado Mutación de estado: la firma del imperativo. Cambiamos el valor de total. El programa "recuerda" porque modificamos una variable. En otros paradigmas esto no existe.
i = i + 1 Avance manual del contador. Somos nosotros quienes lo incrementamos. Si olvidamos esta línea, el bucle es infinito. El paradigma imperativo no hace nada que no le digamos explícitamente.

Dónde se usa

Scripts de automatización

Tareas repetitivas donde el orden de los pasos importa.

Algoritmos de bajo nivel

Control total del flujo para optimizar el rendimiento.

Manipulación de archivos

Procesar línea por línea con control explícito del estado.

Ventajas y desventajas

Ventajas

  • Intuitivo — se piensa como una receta
  • Control total sobre cada paso
  • Eficiente en uso de memoria

Desventajas

  • Difícil de razonar en programas grandes
  • Propenso a efectos secundarios
  • Código difícil de reutilizar
Paradigma 02 / 08

Programación
Procedimental

Evolución del imperativo: en lugar de repetir instrucciones, se agrupan en funciones o procedimientos con nombre. Cada función resuelve una tarea específica y puede llamarse desde cualquier parte del programa. Divide el problema en subproblemas más pequeños. Lenguajes: C, Pascal.

funciones procedimientos modularidad reutilización parámetros llamadas anidadas
Python
# Ordenamiento burbuja con funciones reutilizables
# Cada función tiene una sola responsabilidad

def es_mayor(a, b):
    return a > b

def intercambiar(lista, i, j):
    lista[i], lista[j] = lista[j], lista[i]

def burbuja(lista):
    n = len(lista)
    for i in range(n):
        for j in range(0, n - i - 1):
            if es_mayor(lista[j], lista[j + 1]):
                intercambiar(lista, j, j + 1)
    return lista

def imprimir_resultado(original, ordenada):
    print("Original:", original)
    print("Ordenada:", ordenada)

notas = [7.5, 9.2, 4.8, 8.0, 6.3]
resultado = burbuja(notas.copy())
imprimir_resultado(notas, resultado)
# → Original: [7.5, 9.2, 4.8, 8.0, 6.3]
# → Ordenada: [4.8, 6.3, 7.5, 8.0, 9.2]
¿Por qué esto es procedimental?
def es_mayor(a, b): Una función, una responsabilidad. Solo compara dos valores. No ordena, no imprime, no hace más nada. Esa especialización es la base del paradigma procedimental.
def intercambiar(...) Reutilización. Esta función se puede llamar desde cualquier parte del programa. Sin procedimientos, tendríamos que repetir lista[i], lista[j] = lista[j], lista[i] cada vez.
def burbuja(lista): Composición de procedimientos. Esta función llama a es_mayor e intercambiar. Construimos lógica compleja combinando funciones simples — eso es la esencia del procedimental.
if es_mayor(lista[j], ...) Legibilidad por nombres. Podríamos escribir lista[j] > lista[j+1], pero es_mayor se lee como lenguaje natural. Los nombres de los procedimientos documentan el código.
resultado = burbuja(notas.copy()) Abstracción de complejidad. Toda la lógica del ordenamiento queda oculta dentro de burbuja(). El programa principal no necesita saber cómo funciona — solo la llama.

Dónde se usa

Programas en C

Sistemas embebidos y código de sistema con funciones bien definidas.

Herramientas CLI

Lógica dividida en operaciones específicas y reutilizables.

Procesamiento de datos

Pipelines de transformación con pasos claros y separados.

Ventajas y desventajas

Ventajas

  • Código organizado y reutilizable
  • Más fácil de depurar por partes
  • Divide problemas complejos en tareas

Desventajas

  • Puede haber estado global accidental
  • Escalabilidad limitada en proyectos grandes
  • Sin encapsulamiento real de datos
Paradigma 03 / 08

Orientada
a Objetos

Organiza el código en objetos que combinan datos (atributos) y comportamiento (métodos). Los objetos son instancias de clases y se relacionan mediante herencia, encapsulamiento y polimorfismo. Permite modelar el mundo real directamente en el código.

clases objetos herencia encapsulamiento polimorfismo abstracción
Python
# Figuras geométricas con herencia y polimorfismo
import math

class Figura:
    def __init__(self, color):
        self.__color = color        # Privado — encapsulamiento

    def color(self):
        return self.__color

    def area(self):                 # Abstracto — cada clase lo define
        raise NotImplementedError

    def describir(self):
        return f"{type(self).__name__} {self.__color}: área = {self.area():.2f}"


class Circulo(Figura):
    def __init__(self, color, radio):
        super().__init__(color)
        self.radio = radio

    def area(self):                 # Polimorfismo: mismo nombre, distinto cálculo
        return math.pi * self.radio ** 2


class Rectangulo(Figura):
    def __init__(self, color, ancho, alto):
        super().__init__(color)
        self.ancho = ancho
        self.alto  = alto

    def area(self):
        return self.ancho * self.alto


class Triangulo(Figura):
    def __init__(self, color, base, altura):
        super().__init__(color)
        self.base   = base
        self.altura = altura

    def area(self):
        return (self.base * self.altura) / 2


# Mismo método .describir() en cada objeto — polimorfismo en acción
figuras = [
    Circulo("rojo", 5),
    Rectangulo("azul", 4, 6),
    Triangulo("verde", 3, 8),
]

for f in figuras:
    print(f.describir())
# → Circulo rojo: área = 78.54
# → Rectangulo azul: área = 24.00
# → Triangulo verde: área = 12.00
¿Por qué esto es orientado a objetos?
class Figura: Clase como plantilla. No es un objeto todavía — es el molde. Define qué atributos y métodos tendrán todos los objetos de ese tipo. Solo existe en la memoria cuando creamos una instancia con Figura(...).
self.__color = color Encapsulamiento. Los dobles guiones bajos hacen el atributo privado. Nadie puede escribir figura.__color = "rojo" desde afuera. Solo se accede por el método color(). El objeto controla sus propios datos.
raise NotImplementedError Abstracción. La clase padre sabe que toda figura tiene área, pero no sabe cómo calcularla. Obliga a las subclases a implementar el método. Es un contrato: "si heredás de Figura, debés definir area()".
class Circulo(Figura): Herencia. Circulo recibe gratis todo lo que tiene Figura: el constructor, el método color(), el método describir(). Solo agrega o sobreescribe lo que es diferente.
super().__init__(color) Reutilización del constructor padre. Le delegamos a Figura la inicialización del color. No duplicamos código. La cadena de constructores sube por la jerarquía.
def area(self): return math.pi * ... Polimorfismo: mismo nombre, distinto comportamiento. Circulo, Rectangulo y Triangulo tienen cada uno su area(). El programa no necesita saber cuál es cuál.
for f in figuras: f.describir() Polimorfismo en acción. Llamamos describir() en cada objeto sin preguntar su tipo. Python internamente llama al area() correcto según la clase real de f. Esto se llama dispatch dinámico.

Dónde se usa

Videojuegos

Personajes, objetos y escenarios como clases con comportamientos propios.

Aplicaciones empresariales

Modelos de dominio: Cliente, Factura, Producto encapsulados.

Interfaces gráficas

Botones, ventanas y controles como objetos con eventos y estado.

Ventajas y desventajas

Ventajas

  • Modela el mundo real de forma natural
  • Reutilización por herencia
  • Alta escalabilidad en proyectos grandes

Desventajas

  • Jerarquías profundas difíciles de mantener
  • Overhead innecesario para tareas simples
  • Estado compartido puede causar bugs sutiles
Paradigma 04 / 08

Programación
Funcional

Trata la computación como evaluación de funciones matemáticas puras. Sin estado mutable, sin efectos secundarios. El mismo input siempre produce el mismo output. Las funciones se pasan como argumentos, se devuelven como valores y se componen. Lenguajes: Haskell, Lisp, Erlang.

funciones puras inmutabilidad composición map / filter / reduce lambdas recursión sin efectos secundarios
Python
# Procesar calificaciones con funciones puras
# Ninguna función modifica los datos originales
from functools import reduce

calificaciones = [4.5, 8.2, 9.0, 3.7, 7.5, 8.8, 5.1, 9.5]

# Funciones puras: mismo input → mismo output, siempre
aprobado      = lambda nota: nota >= 6.0
al_porcentaje = lambda nota: round((nota / 10) * 100, 1)
sumar         = lambda a, b: a + b

# Composición: filtrar → transformar → reducir
aprobados   = list(filter(aprobado, calificaciones))
porcentajes = list(map(al_porcentaje, aprobados))
total       = reduce(sumar, porcentajes, 0)
promedio    = total / len(porcentajes)

def estadisticas(notas):            # También pura: no modifica 'notas'
    ordenadas = sorted(notas)
    return {
        "min":   ordenadas[0],
        "max":   ordenadas[-1],
        "media": reduce(sumar, notas, 0) / len(notas),
    }

print("Aprobados: ", aprobados)
print("Promedio:  ", promedio, "%")
print("Stats:     ", estadisticas(aprobados))
# → Aprobados:  [8.2, 9.0, 7.5, 8.8, 9.5]
# → Promedio:   86.0 %
# → Stats:      {'min': 7.5, 'max': 9.5, 'media': 8.6}
¿Por qué esto es funcional?
lambda nota: nota >= 6.0 Función pura. Depende solo de su argumento nota. No lee ni escribe variables externas. Con el mismo input siempre da el mismo output — sin sorpresas.
filter(aprobado, calificaciones) Función de orden superior. filter recibe otra función como argumento. En programación funcional, las funciones son datos: se guardan en variables, se pasan, se devuelven.
list(map(al_porcentaje, aprobados)) Transformación sin mutación. No modificamos aprobados. Creamos una lista nueva con los valores transformados. Los datos originales quedan intactos — eso es inmutabilidad.
reduce(sumar, porcentajes, 0) Reducción. Colapsamos toda la lista a un solo valor aplicando sumar acumulativamente: ((82+90)+75)+... El estado intermedio nunca se almacena — es una expresión, no una secuencia de pasos.
sorted(notas) dentro de estadisticas() Inmutabilidad garantizada. sorted() devuelve una lista nueva. La función no toca notas. Si la llamamos 10 veces con los mismos datos, el resultado es siempre el mismo y los datos originales nunca cambian.

Dónde se usa

Procesamiento de datos

Transformaciones en pipelines: ETL, análisis, reportes.

Concurrencia

Sin estado mutable, no hay condiciones de carrera al paralelizar.

Testing

Funciones puras son trivialmente testeables — sin mocks ni setup.

Ventajas y desventajas

Ventajas

  • Código predecible y fácil de probar
  • Seguro en contextos concurrentes
  • Composición produce código conciso

Desventajas

  • Curva alta (mónadas, recursión profunda)
  • Puede crear muchas copias de datos en memoria
  • No encaja bien con I/O o estado inherente
Paradigma 05 / 08

Programación
Declarativa

Describes qué querés obtener, no cómo lograrlo. El programador declara el objetivo y el motor o intérprete decide la mejor estrategia. SQL es el ejemplo más conocido: describes la consulta y la base de datos decide si usar un índice, un escaneo completo, etc.

qué vs cómo expresiones sin efectos secundarios alto nivel de abstracción el motor optimiza
SQL
-- Tabla: estudiantes
-- id | nombre       | nota | carrera
-- ---|--------------|------|----------
-- 1  | Ana García   | 9.2  | Sistemas
-- 2  | Luis Mora    | 7.5  | Informática
-- 3  | Sara López   | 8.8  | Sistemas
-- 4  | Pedro Ruiz   | 5.9  | Sistemas

-- Declaramos QUÉ queremos — el motor decide CÓMO buscarlo
SELECT
    nombre,
    nota,
    CASE
        WHEN nota >= 9.0 THEN 'Sobresaliente'
        WHEN nota >= 7.0 THEN 'Notable'
        ELSE 'Aprobado'
    END AS distincion
FROM estudiantes
WHERE carrera = 'Sistemas'
  AND nota >= 6.0
ORDER BY nota DESC;

-- Resultado:
-- Ana García  | 9.2 | Sobresaliente
-- Sara López  | 8.8 | Notable
¿Por qué esto es declarativo?
SELECT nombre, nota Declaramos QUÉ queremos ver. No decimos "iterá la tabla, abrí cada fila, copiá el campo nombre...". Solo declaramos los campos del resultado. El motor decide cómo extraerlos.
WHERE carrera = 'Sistemas' AND nota >= 6.0 Condición declarada, no código de búsqueda. El motor decide si usar un índice, un full scan, un hash join, etc. Nosotros nunca escribimos el algoritmo de filtrado.
ORDER BY nota DESC Resultado deseado, no algoritmo de ordenamiento. No programamos bubble sort ni merge sort. Declaramos el orden y el motor elige el algoritmo más eficiente para esos datos.
CASE WHEN nota >= 9.0 THEN ... Lógica como expresión, no como secuencia. En imperativo escribiríamos: variable temporal, if/else, asignación. Aquí es una sola expresión declarativa que el motor evalúa internamente.
HTML + CSS
<!-- Declaramos ESTRUCTURA y ESTILO, no el algoritmo de render -->
<style>
  .tarjeta {
    display: flex;       /* El navegador decide cómo distribuir */
    gap: 16px;
    border-radius: 8px;
    padding: 20px;
  }
  .nota-alta { color: green; font-weight: bold; }
</style>

<div class="tarjeta">
  <span>Ana García</span>
  <span class="nota-alta">9.2</span>
</div>
¿Por qué esto es declarativo? (HTML/CSS)
<div class="tarjeta"> Estructura, no algoritmo. Declaramos que esto es una "tarjeta". El navegador decide cómo construir el árbol DOM, la memoria necesaria y el proceso de renderizado — nosotros no escribimos ese código.
display: flex; gap: 16px; Intención de layout, no cálculo. No programamos la distribución de posiciones ni el bucle para colocar cada elemento. CSS recibe la intención y el motor de layout del navegador hace los cálculos geométricos.
class="nota-alta" Categoría semántica, no comando. No decimos "ponéle color verde a este span". Declaramos que pertenece a la categoría nota-alta. El estilo es una consecuencia de esa declaración, aplicada por el motor de estilos.
color: green; font-weight: bold; Estado deseado, no pasos. El equivalente imperativo sería: element.style.color = "green"; element.style.fontWeight = "bold". CSS declara el resultado final; el navegador decide cuándo y cómo aplicarlo, incluyendo cascada e herencia.

Dónde se usa

Bases de datos (SQL)

Consultas complejas sin escribir algoritmos de búsqueda.

Interfaces web (HTML/CSS)

Estructura y estilo sin código de renderizado manual.

Infraestructura (Terraform)

Declarar el estado deseado del sistema, no los pasos para llegar.

Ventajas y desventajas

Ventajas

  • Código muy legible y conciso
  • El motor puede optimizar mejor que nosotros
  • Menos errores de lógica de control

Desventajas

  • Menor control sobre el rendimiento
  • Depuración más difícil (el motor es opaco)
  • Dependiente de las capacidades del intérprete
Paradigma 06 / 08

Programación
Reactiva

El programa reacciona a flujos de datos y eventos en lugar de ejecutar instrucciones en orden fijo. Los componentes se suscriben a fuentes de datos y se actualizan automáticamente cuando algo cambia. Es la base de frameworks modernos como React y Vue. Lenguaje representativo: JavaScript.

flujos de datos eventos observadores suscriptores asincronía propagación de cambios
JavaScript
// Monitoreo de temperatura con patrón Observador
// Los suscriptores reaccionan cuando el dato cambia

class FlujoDatos {
  constructor() {
    this._subs = {};
  }

  on(evento, fn) {
    if (!this._subs[evento]) this._subs[evento] = [];
    this._subs[evento].push(fn);
    return this;
  }

  emitir(evento, datos) {
    (this._subs[evento] || []).forEach(fn => fn(datos));
  }
}

const sensor = new FlujoDatos();

// Cada suscriptor define su propia reacción
sensor.on('temperatura', temp => {
  if (temp > 37.5) console.log(`ALERTA: fiebre (${temp}°C)`);
});

const historial = [];
sensor.on('temperatura', temp => {
  historial.push({ temp, hora: new Date().toLocaleTimeString() });
  console.log(`Registrado: ${temp}°C — total: ${historial.length} lecturas`);
});

sensor.emitir('temperatura', 36.5);
// → Registrado: 36.5°C — total: 1 lecturas

sensor.emitir('temperatura', 38.2);
// → ALERTA: fiebre (38.2°C)
// → Registrado: 38.2°C — total: 2 lecturas
¿Por qué esto es reactivo?
this._subs = {} Registro de suscriptores. El núcleo del patrón reactivo: un mapa de "¿quién quiere saber qué?". Los emisores no conocen a sus receptores — solo notifican por nombre de evento. Esto es desacoplamiento total.
sensor.on('temperatura', fn) Suscripción a un flujo. El suscriptor dice "avísame cuando llegue un dato de temperatura". No pregunta activamente (polling) — el sistema lo llama cuando el dato cambia. Esto es la esencia reactiva: reacción vs. consulta.
sensor.emitir('temperatura', 38.2) Propagación de cambio. Un solo emit dispara todos los suscriptores de ese evento en orden. El emisor no sabe cuántos son ni qué hacen — máximo desacoplamiento. En React/Vue esto ocurre al mutar el estado.
if (temp > 37.5) console.log(`ALERTA...`) Lógica independiente por suscriptor. Cada receptor define su propia reacción sin afectar a los demás. Se pueden agregar o quitar suscriptores sin tocar el emisor — la arquitectura se extiende sin modificar el código existente.
historial.push({ temp, hora: ... }) Dos suscriptores al mismo flujo. La alerta y el historial escuchan el mismo evento pero reaccionan diferente. En una UI, esto equivale a que el gráfico, el indicador y el log se actualicen solos cuando llega el mismo dato nuevo.

Dónde se usa

Interfaces reactivas

React, Vue: la UI se actualiza sola cuando cambia el estado.

Streaming de datos

Eventos en tiempo real: precios bursátiles, mensajes, sensores.

Sistemas IoT

Dispositivos que reaccionan a lecturas de sensores al instante.

Ventajas y desventajas

Ventajas

  • Maneja la asincronía elegantemente
  • Desacoplamiento entre emisores y receptores
  • Ideal para múltiples fuentes de datos

Desventajas

  • El flujo de datos es difícil de rastrear
  • Cascadas de eventos generan bugs sutiles
  • Curva alta con RxJS y Observables
Paradigma 07 / 08

Programación
Lógica

Basado en lógica formal: defines hechos y reglas, y un motor de inferencia calcula las respuestas. No programas el camino hacia la solución — declaras lo que sabes y dejas que el motor explore con backtracking todas las combinaciones posibles. Lenguaje: Prolog.

hechos reglas consultas backtracking unificación motor de inferencia
Prolog — Relaciones familiares
% === HECHOS: lo que sabemos que es verdad ===
progenitor(carlos, ana).
progenitor(carlos, luis).
progenitor(ana,    sofia).
progenitor(ana,    miguel).
progenitor(luis,   paula).

masculino(carlos).  masculino(luis).   masculino(miguel).
femenino(ana).      femenino(sofia).   femenino(paula).

% === REGLAS: relaciones que se derivan ===
% "X :- Y" se lee: X es verdad SI Y es verdad
padre(X, Y)   :- progenitor(X, Y), masculino(X).
madre(X, Y)   :- progenitor(X, Y), femenino(X).
abuelo(X, Z)  :- progenitor(X, Y), progenitor(Y, Z).
hermano(X, Y) :- progenitor(Z, X), progenitor(Z, Y), X \= Y.

% Recursiva: ancestro en cualquier generación
ancestro(X, Y) :- progenitor(X, Y).
ancestro(X, Y) :- progenitor(X, Z), ancestro(Z, Y).

% === CONSULTAS — el motor infiere las respuestas ===
% ?- padre(carlos, ana).       →  true
% ?- abuelo(carlos, sofia).    →  true
% ?- hermano(sofia, X).        →  X = miguel
% ?- ancestro(carlos, paula).  →  true  (carlos→luis→paula)
¿Por qué esto es lógico?
progenitor(carlos, ana). Hecho. Una afirmación incondicional: "carlos es progenitor de ana". No hay asignación de variables ni pasos a seguir. El motor de inferencia almacena esto como verdad absoluta en su base de conocimiento.
padre(X, Y) :- progenitor(X, Y), masculino(X). Regla. Se lee: "X es padre de Y si X es progenitor de Y y X es masculino". El operador :- es el "si" lógico. Declaramos la relación; el motor deduce quién cumple la condición.
abuelo(X, Z) :- progenitor(X, Y), progenitor(Y, Z). Composición de hechos. La relación abuelo se define como dos relaciones progenitor encadenadas a través de un Y intermedio. El motor buscará automáticamente todos los Y posibles usando backtracking.
ancestro(X, Y) :- progenitor(X, Z), ancestro(Z, Y). Recursividad lógica. ancestro se define en términos de sí mismo. El motor de inferencia recorre el árbol familiar a cualquier profundidad sin que nosotros programemos el recorrido ni los casos de parada explícitamente.
?- hermano(sofia, X). Consulta con variable libre. X es una incógnita. Prolog busca qué valor hace verdadera la regla. No ejecutamos procedimientos — respondemos preguntas. El motor prueba todas las posibilidades con backtracking y devuelve las que funcionan.
Prolog — Colorear un mapa (restricciones)
% Regiones adyacentes no pueden tener el mismo color
color(rojo).  color(verde).  color(azul).

adyacente(a, b).  adyacente(b, c).
adyacente(a, c).  adyacente(c, d).

colorear(CA, CB, CC, CD) :-
    color(CA), color(CB), color(CC), color(CD),
    CA \= CB,   CB \= CC,   CA \= CC,   CC \= CD.

% ?- colorear(CA, CB, CC, CD).
% El motor aplica backtracking sobre todas las combinaciones
% → CA=rojo, CB=verde, CC=azul, CD=rojo  (entre otras soluciones)
¿Por qué esto es lógico? (restricciones)
color(rojo). color(verde). color(azul). Dominio declarado como hechos. No creamos arrays ni enumeraciones — son hechos que el motor usa para generar candidatos automáticamente. El dominio de posibilidades es conocimiento, no una estructura de datos.
adyacente(a, b). adyacente(b, c). ... Restricciones del problema como hechos. El grafo de adyacencia es conocimiento declarativo. No escribimos una función que chequee vecinos — Prolog consulta estos hechos durante el backtracking para validar candidatos.
color(CA), color(CB), color(CC), color(CD) Generación por backtracking. El motor prueba cada combinación de colores para CA, CB, CC, CD. Son 3⁴ = 81 combinaciones posibles — nosotros no escribimos ese código de prueba exhaustiva. El motor lo hace solo.
CA \= CB, CB \= CC, CA \= CC, CC \= CD Restricciones declaradas, poda automática. Decimos qué debe ser falso. Cuando el motor encuentra una combinación que viola una restricción, hace backtracking inmediato y prueba la siguiente opción. No programamos ese rechazo.

Dónde se usa

Sistemas expertos

Diagnóstico médico o legal basado en reglas de conocimiento.

IA simbólica

Razonamiento formal, planificación automática de tareas.

Restricciones (CSP)

Horarios, asignaciones, Sudoku — el motor encuentra soluciones.

Ventajas y desventajas

Ventajas

  • Muy expresivo para modelar relaciones

Concurrente y Paralela

Diseña programas que ejecutan múltiples tareas al mismo tiempo. La concurrencia intercala tareas que progresan independientemente (no necesariamente al mismo instante), mientras que el paralelismo las ejecuta literalmente en simultáneo usando múltiples núcleos. Lenguajes: Go (concurrente), CUDA (paralela en GPU).

Go — goroutines y canales
// Descargar 5 páginas concurrentemente
// Sin goroutines: ~5s. Con goroutines: ~1s.

package main

import (
    "fmt"
    "sync"
    "time"
)

func descargar(url string, id int, wg *sync.WaitGroup, res chan<- string) {
    defer wg.Done()
    time.Sleep(1 * time.Second)  // simula latencia de red
    res <- fmt.Sprintf("Descargado [%d]: %s", id, url)
}

func main() {
    urls := []string{
        "fidelitas.ac.cr/cursos",
        "fidelitas.ac.cr/noticias",
        "fidelitas.ac.cr/biblioteca",
        "fidelitas.ac.cr/campus",
        "fidelitas.ac.cr/horarios",
    }

    resultados := make(chan string, len(urls))
    var wg sync.WaitGroup
    t0 := time.Now()

    for i, url := range urls {
        wg.Add(1)
        go descargar(url, i+1, &wg, resultados)  // 'go' lanza una goroutine
    }

    go func() { wg.Wait(); close(resultados) }()

    for r := range resultados {
        fmt.Println(r)
    }
    fmt.Printf("Total: %.2fs  (sin go: ~5s)\n", time.Since(t0).Seconds())
}
// El orden de llegada es no-determinista:
// → Descargado [3]: fidelitas.ac.cr/biblioteca
// → Descargado [1]: fidelitas.ac.cr/cursos  ...
// → Total: 1.00s
¿Por qué esto es concurrente?
go descargar(url, i+1, &wg, resultados) Lanzamiento de goroutine. La palabra clave go lanza la función en una goroutine independiente — una unidad de ejecución extremadamente ligera (~2 KB de stack inicial). El bucle continúa sin esperar que termine. Esto es lo que hace el código concurrente.
resultados := make(chan string, len(urls)) Canal tipado. Los canales son el mecanismo de comunicación entre goroutines. En lugar de compartir memoria (fuente de race conditions), las goroutines se envían mensajes a través del canal. Es el lema de Go: "No comuniques compartiendo memoria; compartí memoria comunicando".
defer wg.Done() Coordinación con WaitGroup. Cada goroutine avisa cuando termina. defer garantiza que Done() se llame aunque la función falle con un panic. Sin coordinación explícita no sabríamos cuándo terminaron todas.
res <- fmt.Sprintf(...) Envío al canal. La goroutine deposita su resultado. Si el canal estuviera lleno, se bloquearía aquí — sincronización implícita. El canal serializa los accesos concurrentes de forma segura sin necesidad de locks explícitos.
// El orden de llegada es no-determinista No-determinismo inherente. Las goroutines terminan según el scheduler del SO y la red. El comportamiento exacto varía entre ejecuciones — y está diseñado así. En concurrencia no se garantiza orden, solo completitud.
Python — Race condition y su solución
# El bug clásico de concurrencia y cómo prevenirlo
import threading

# ❌ SIN lock — resultado impredecible
contador_inseguro = 0

def incrementar_inseguro():
    global contador_inseguro
    for _ in range(100_000):
        contador_inseguro += 1   # leer-modificar-escribir NO es atómico

# ✅ CON lock — resultado garantizado
contador_seguro = 0
lock = threading.Lock()

def incrementar_seguro():
    global contador_seguro
    for _ in range(100_000):
        with lock:               # solo un hilo a la vez entra aquí
            contador_seguro += 1

# Lanzar 5 hilos para cada versión
hi = [threading.Thread(target=incrementar_inseguro) for _ in range(5)]
hs = [threading.Thread(target=incrementar_seguro)   for _ in range(5)]

for h in hi: h.start()
for h in hi: h.join()

for h in hs: h.start()
for h in hs: h.join()

print(f"Esperado:   500,000")
print(f"Sin lock:   {contador_inseguro:,}   ← distinto en cada ejecución")
print(f"Con lock:   {contador_seguro:,}   ← correcto siempre")
# → Sin lock:   347,821
# → Con lock:   500,000
¿Por qué esto es concurrente? (race condition)
contador_inseguro += 1 Operación no atómica. Esta línea son 3 pasos a nivel CPU: leer el valor, sumarle 1, escribirlo de vuelta. Si dos hilos leen el mismo valor antes de que alguno escriba, ambos escriben el mismo incremento y se pierde una cuenta. Esto es el race condition.
threading.Thread(target=incrementar_inseguro) Hilo de sistema operativo. A diferencia de goroutines de Go (~2KB), los threads de Python mapean a threads del SO (~1MB de stack). Todos comparten el mismo espacio de memoria del proceso — ahí nace el peligro cuando acceden a variables globales.
lock = threading.Lock() Mutex (exclusión mutua). Solo un hilo puede tener el lock en un momento dado. Los demás se bloquean esperando en with lock:. Es la solución fundamental al race condition — pero serializa el acceso y tiene costo de rendimiento.
with lock: contador_seguro += 1 Sección crítica protegida. El bloque with lock: garantiza que solo un hilo ejecuta el incremento a la vez. Los 3 pasos CPU (leer, sumar, escribir) ahora suceden atómicamente desde la perspectiva del programa.
for h in hi: h.join() Sincronización al final. join() bloquea el hilo principal hasta que cada hilo termine. Sin esta sincronización el programa principal podría imprimir los contadores antes de que los hilos hayan terminado de incrementar.

Dónde se usa

Servidores web

Atender miles de peticiones simultáneas sin bloquear.

GPU / CUDA

Miles de núcleos ejecutando operaciones matriciales en paralelo.

Aplicaciones de escritorio

UI fluida mientras operaciones costosas corren en segundo plano.

Ventajas y desventajas

Ventajas

  • Aprovecha todos los núcleos del procesador
  • Reduce tiempos en tareas de I/O intensivo
  • Sistemas más responsivos y escalables

Desventajas

  • Race conditions y deadlocks muy difíciles de depurar
  • Mayor complejidad de diseño y pruebas
  • La sincronización excesiva anula la ganancia
